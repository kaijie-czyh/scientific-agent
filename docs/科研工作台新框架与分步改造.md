# 科研工作台：新框架与分步改造

日期：2026-10-16。范围：先搭建可运行、可持久化的工作台基础，再逐模块迁入真实能力。

> 导航整合已按原界面完成，当前入口、合并关系与验收范围以《导航与研究流程调整说明.md》为准。下文“五个工作区”是早期方案，不作为当前页面布局；原 `/` 和 `/workspace` 仍使用同一套界面。

> **本轮纠偏（以此为准）**：用户明确要求基于原系统增量修改，不另建一套 UI。
> 原来的 `/` 为主界面，`/workspace` 现在也返回同一原界面。
> 保留深蓝侧栏、顶部流程条、论文浏览、灵感笔记、人工节点与下载入口；
> 科研指导通过 `research-guide.{js,css}` 作为可收起右侧面板接入。
> 下文五区设计仅作为内部能力划分参考，不再用来重排用户的全部页面和导航。
> 之前的工作台讨论与研究记录保留在右侧“研究记录”，不删除，不强制重新录入。
> 指导上下文已接入原系统笔记、思路、缺口、论断和实验摘要；指导答复可由用户存入原来的灵感笔记。
> 后续按原模块逐项改进业务逻辑；报告、Claim 等先改善用途与关联，不直接废弃。
>
> 纠偏验收：38 项回归测试通过；原笔记保存、刷新恢复、指导读取笔记及存回笔记均已浏览器实测。
> 快速切页采用独立视图容器，避免过期异步响应混入新页面；侧栏笔记也会拦截过期响应。
> 375px 窄屏实测无横向溢出；小屏指导面板可收起，不强行挤压业务页面。
> 效果图：`docs/original-ui-integrated-preview.jpg`。演练数据仅新增到独立演练项目中。

## 1. 产品与本轮交付

面向有课题、论文或实验材料的研究者。帮助用户明确研究问题、核对依据、安排工作、记录结果和组织写作。
首次重点验证联邦学习／AI 安全的实验型课题。通用界面与数据契约不代表所有领域都已验证适配。

新入口：`/workspace`。现有入口 `/` 保留，并增加工作台链接。
框架不自动启动旧 Pipeline，也不把旧的 VERIFIED 状态迁移为用户已经确认的科学结论。

本轮实际实现：

- 五个工作区、右侧上下文指导、项目选择与创建、项目条件保存。
- 读取已有论文库，复用本地论文上传，选择论文或研究记录作为对话上下文。
- 问题 → 方案 → 用户执行与提交结果 → 用户判断 → 写作骨架的手动记录闭环。
- 对话历史、待采纳建议、正式记录分开持久化；只有用户点击采纳才保存建议产物。
- 修订保留旧版，传递依赖复核标记；并发提交检查版本，不覆盖较新的研究记录。
- Markdown 研究记录与 JSON 完整记录导出。

尚未迁入：新工作台里的自动选题检索、逐段精读、自动实验指标分析、完整稿件生成与投稿检查。
自动检索与原有产物仍从现有页面使用。新工作台明确列出这些状态，不把手动登记闭环描述为全自动科研完成。

## 2. 页面结构与右侧指导

| 工作区 | 中间主要内容 | 右侧指导负责什么 | 当前成果 |
| --- | --- | --- | --- |
| 项目总览 | 研究兴趣、目标、已有基础、设备、时间、下一步、待复核记录数 | 补充约束，安排最小下一步，判断范围是否过大 | 项目条件 |
| 文献阅读 | 已有文献、原文入口、上传、阅读笔记 | 根据阅读目的解释论文，区分原文与推断，帮助找基线与局限 | 带来源的笔记 |
| 研究问题 | 候选问题、已有依据、待检验设想、最接近工作与未核实内容 | 比较设想、缩小问题、针对性安排查证 | 研究问题卡 |
| 方案与实验 | 方案、实际结果、研究判断 | 检查对照、预算和指标，区分运行失败与反驳假设 | 任务方案、结果与用户判断 |
| 成果写作 | 写作骨架、依据、待补证据 | 梳理论证顺序、检查过度表述与缺失证据 | 写作骨架 |

对话不是需要逐条填完的问卷。一次只推进用户当前最关心的事，最多追问两个关键条件。
用户能直接在中间填写，也能通过对话整理成建议再采纳；两种方式保存到同一套研究记录。

指导的输入：当前工作区、项目条件、选中的记录、最近的有效研究记录、最近对话，以及选中的至多三篇论文。
未选论文时只取少量近期论文摘要；选中论文时允许附少量已存储文本片段。界面不声称这些片段覆盖全文。
论文题名、关键术语保持原文，解释默认使用中文。

指导的输出：当前答复、核实过 ID 存在的论文引用、少量追问、可选的产物草案。
草案可为笔记、问题、方案或骨架；不能产生实验结果，不能自动批准科学结论。
建议会显示原文内容供用户审阅，项目变化后不能直接采纳旧上下文里的建议。

模型可用时沿用现有任务路由和密钥配置。`dry_run=true` 时显示规则模式，不调用模型、不伪造检索结果。
模型失败时返回明确错误并保留输入，不偷偷改用“看起来像模型回复”的占位内容。

## 3. 现有知识点如何成为底层逻辑

### 阅读

来源：`web/static/app.js` 原有阅读方法页。新增共享模块 `core/knowledge/reading_methodology.py`。

保留 Why、What、How、Result、Weakness、Ideas 六问；按了解方向、理解方法、寻找基线、寻找切入点、解决实验问题取用。
六问是可选择的观察角度，不是每篇必填表。不给所有研究统一规定阅读比例或论文数量。
每条重要判断区分：作者事实、作者解释、用户想法、模型推断；有出处时附真实位置，无出处标待核实。
下一轮将这些规则接到自动阅读卡与证据片段检索，避免只做页面上的知识介绍。

### 创新

来源：`core/knowledge/innovation_playbook.py`。

应用、修改、融合、比较、理论五类用于内部启发，不要求每类凑一个题目。
候选问题需要说明：已有方法 → 真实局限或边界 → 拟研究的差异 → 最小检验 → 尚未核实部分。
已修正“新问题＋新方法必然顶刊”等表述。类型和矩阵不能决定创新分数、发表档次或录用概率。
缺少摘要、指标或解析片段不等于科学空白，不能把系统的知识缺口直接写成领域缺口。
真实新颖性核查需要后续接入针对性检索，并记录检索范围与最接近文献。

### 写作

来源：`core/knowledge/writing_methodology.py` 与原有写作方法页。

保留：一句核心思想、可检验贡献、先组织证据、分段起草、逆向提纲、逐条核对贡献、领域适配。
已修正“必须实验正向成功才能写作”和“不回头”约束：背景与方法可提前写，负面结果可形成论证；允许修订并保留版本。
最终结果描述必须有相应材料，预期指标不能进入结果章节。
本轮先用于指导和骨架，完整起草与审计下一轮再接入。

## 4. 数据与状态

项目条件、研究记录、对话、建议分别建模，保存在现有项目 SQLite 的 `research_workspace.v1` KV 中。
保留现有论文实体和存储，不复制论文。工作台暂不迁移旧 Idea/Claim/Experiment 的状态，避免混淆判定含义。

| 记录 | 必要关联与约束 |
| --- | --- |
| 笔记 | 可关联论文、问题、方案或结果；用户想法不自动成为文献事实 |
| 问题 | 允许无文献的早期草案，但不声称新颖性已核实 |
| 方案 | 必须关联有效研究问题 |
| 结果 | 必须关联有效方案；显式填写运行状态；已完成的计算实验须提供有限数值指标 |
| 研究判断 | 必须关联结果；用户选择支持、反驳或无法定论，明确未经系统独立验证 |
| 写作骨架 | 允许任意阶段整理；已有结论通过关联记录说明，缺证据保留待办 |

没有统一“已完成全部科研”开关。记录可继续补充；新版本引用旧版本的下游记录会被拒绝，防止循环依赖。
问题或方案修订后，直接与间接依赖均标记待复核。后续只能关联有效且不需复核的记录。
旧记录继续留在历史中；不删除实验，不抹掉被反驳的设想。

并发控制：每次写操作携带 `expected_revision`，SQLite 事务内比较与保存。
跨窗口的旧提交返回 409；前端保留草稿，用户刷新后重新核对。
页面没有定时全量重绘；对话生成期间仍可浏览其他工作区，晚返回的回复不会写到另一个项目的界面。

## 5. 联邦学习验收旅程

1. 创建“联邦学习”项目，保存目标、PyTorch 基础、设备与两个月时间约束。
2. 用已有检索或上传导入真实文献；确认摘要／全文解析范围。
3. 阅读并记录数据非 IID、更新裁剪、攻击者可见信息等与当前问题相关的证据与疑问。
4. 讨论问题草案“不同数据差异下，更新裁剪对成员推断风险与分类性能的影响”。先核对相近工作，不预设它新颖。
5. 保存最小试跑方案，说明基线、数据划分、训练预算、攻击条件与支持／反驳标准。
6. 用户执行实验，登记实际指标或运行失败；系统不从运行状态推断假设真伪。
7. 用户判断支持、反驳或无法定论，必要时修订问题／方案并补实验。
8. 根据已有材料整理骨架，缺少依据的结论留空，导出记录供汇报。

软件验收中的联邦学习指标是独立临时数据库里的测试夹具，不会进入用户项目或被当成科研发现。

## 6. 分部分改造顺序

| 顺序 | 本部分的具体工作 | 完成判据 |
| --- | --- | --- |
| 1，本轮 | 五区界面、右侧指导、共享方法论、持久化与研究记录闭环 | 问题到骨架可手动贯通；重启恢复；错误与旧版本不覆盖数据 |
| 2，下一部分 | 把真实选题与检索迁入；先补充用户约束，再规划查询，分批展示结果 | 证据可点开；能停止扩展；失败说明来源与原因；不能用模板冒充检索结果 |
| 3 | 阅读卡、原文片段定位、论文对比与最接近工作核查；将报告改成可更新研究现状 | 关键判断定位原文；摘要与全文区别明确；用户阅读笔记能进入问题讨论 |
| 4 | 结构化问题卡与可行性检查，问题讨论与创新知识规则结合 | 每个候选说明具体差异、证据与最小验证；不强制生成固定数量方向 |
| 5 | 结构化实验任务、配置／结果文件导入、指标分析与反证；修复旧回填续跑问题 | 导入后必经重新分析；判断有解释；失败／负面结果可继续研究 |
| 6 | 分段写作、论证检查、引用核验与投稿准备 | 每条结果论断有依据；待核实项明确；不以假设成立作为进入写作的条件 |
| 7 | 服务器部署准备：登录与项目权限、后台任务、备份、配额、日志、异常恢复 | 多用户隔离；刷新不取消任务；重启不丢记录；成本与时长可控 |

每次只迁入一部分。迁入前先复核旧功能与测试，迁入后用同一个联邦学习项目串联验收，再做下一部分。
现有架构的 Agent/Tool/Artifact 可继续作为内部实现，页面呈现用户任务与判断，不直接呈现底层节点名称。

## 7. 代码落点

- `core/workspace/schema.py`：正式记录、对话、草案的数据契约。
- `core/workspace/service.py`：持久化、版本比较、依赖校验、修订与导出。
- `core/workspace/guide.py`：页面与项目上下文组装、共享方法论、模型／规则指导。
- `web/workspace_api.py`：项目级接口。
- `web/static/workspace.{html,css,js}`：独立框架界面。
- `tests/test_research_workspace.py`：手动闭环、负面结果、修订传递、恢复、并发、采纳与模型异常行为测试。

本轮验证范围是框架和接口，不代表已实测真实模型的科研质量或完成了一项真实联邦学习实验。
